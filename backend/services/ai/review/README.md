# Пайплайн рекомендацій, фаза 4a

Самостійний CommonJS-модуль. Приймає лише `blocks` із контракту документа та `meta: { title?, courseName? }`; не потребує locator, формату файлу чи моделей БД.

```js
const { runReview, generateSuggestion, PROMPT_VERSION } = require('./services/ai/review');

const { findings, rubricSummary, stats } = await runReview({ blocks, meta,
  options: { concurrency: 2, minConfidence: 0.7, maxFindings: 10, maxPerGroup: 3 },
});
const suggestion = await generateSuggestion({ finding: findings[0], blocks, meta,
  feedback: 'Зробіть формулювання коротшим.', // необов’язковий Refine
  validateOps: documentValidateOps, // необов’язково: (blocks, ops) => errors[]
});
```

`runReview` повертає `Finding[]` за контрактом фази 4a. `id` стабільний для пари критерій + відсортовані evidenceBlockIds. `materiality` — короткий текст про наслідок проблеми, `mba27` — канонічні ID з картки критерію або null. `rubricSummary.verdicts` зберігає всі вердикти **до verifier**, включно з `ok`, `not_applicable` та `not_evaluated` для невдалих груп, та джерело `deterministic|diagnose`; `coverage` містить зв’язки MBA-27 → outcomes → assessments, прямі оцінювання й прогалини. `stats` містить фактичну кількість викликів з урахуванням повторів, кандидатів, відкинутих знахідок, тривалість, `degraded: ['structure'|'verify']` та `failedGroups` з назвами невдалих груп.

Етапи:

0. `checks.js`: відсутні розділи з урахуванням синонімів, AI-політика, сума однозначних компонентних ваг. Confidence = 1. Не додає шкалу оцінок, штрафи, total чи неоднозначні вкладені ваги.
1. `structure.js`: один виклик для структури з blockIds; матрицю покриття обчислює код лише за явно витягнутими зв’язками. Якщо повтори не допомогли, аналіз триває з порожньою структурою та порожніми зв’язками покриття; `stats.degraded` містить `structure`.
2. `diagnose.js`: п’ять груп рубрики, не більше `concurrency` одночасно, включно з повторами. Пропускає `disabled: true`; відсутній, зайвий або подвійний вердикт є семантичною помилкою. Після невдалої корекції група пропускається: її критерії мають `not_evaluated` (навіть якщо для них є окрема детермінована знахідка), групу записуємо в `stats.failedGroups`. Детерміновані знахідки зберігаються та проходять подальші фільтри й caps.
3. `verify.js`: окремий критик з `reasoning.effort: low`, потім валідація доказів, поріг confidence, severity, dedup, сортування severity rank × confidence і caps. Параметри можуть зменшити caps; верхня межа — 10 загалом і 3 на групу. Для відсутнього розділу дозволено найближчий заголовок або `document`; для решти потрібні реальні blockIds. Зміна severity не більше одного рівня з причиною, яку зберігаємо в rationale.
4. `rewrite.js`: один виклик на пропозицію, максимум два повтори з попередньою відповіддю та точними помилками. Тільки повний новий текст абзацу та `replaceBlock|insertAfter|deleteBlock`. Локальна валідація завжди перевіряє існування, readOnly, непорожній текст і дублікати; інжектований валідатор може додати перевірки документа.

`fixType: question` спочатку дає коротке питання українською без ops. Feedback із відповіддю викладача дозволяє сформувати правку. Якщо три спроби невалідні, повертається порада `kind: edit, applicable: false` без ops та question; точні помилки доступні у `validationErrors`. Помилки API не маскуються під успішний результат.

Клаузули збирає код із `standardClauses`: модель обирає якір/операцію та заповнює лише відомі placeholders буквальними даними з документа чи feedback. Решта тексту незмінна. Варіант з невідомими параметрами має `ops: []`; його rationale просить уточнення. `choice.applicable` істинний, коли є хоча б один варіант з ops; застосовувати можна лише такий варіант. Чернетки явно позначено в description, вони не подаються як затверджений текст KSE. Наявний абзац політики можна замінити замість додавання суперечливого дубліката.

Промпти англійські: роль, правила й `renderCriteriaCards` у статичному system-повідомленні; факти та документ `[b0042] text` — далі. Тексти для викладача українські, вставки у силабус англійські. Усі виклики через `client.createResponse`, strict `json_schema`: кожне поле обов’язкове, кожен object має `additionalProperties: false`, nullable через union. Версія: `review-4a-v1`.

`requestJSON` робить максимум два додаткові виклики після тимчасових помилок мережі, timeout, HTTP 408/429/5xx або неповних/невалідних/schema-invalid відповідей. Для API-збоїв є коротка затримка 250/500 мс; постійні HTTP-помилки не повторюються. Семантична валідація має окрему одну корекцію: точна помилка додається до user-повідомлення, статична частина лишається незмінною. Бюджети не скидаються між спробами: максимум 4 виклики при поєднанні форматних/API та семантичних помилок.

Якщо verifier так і не відповів коректно, `stats.degraded` містить `verify`; лишаємо детерміновані знахідки та diagnose-знахідки з confidence ≥ 0.9, потім застосовуємо ту саму валідацію evidence, поріг налаштувань, severity, dedup, сортування й caps. Це результат без семантичного підтвердження критиком. `runReview` кидає помилку лише для невалідних blocks або відмови всіх активних diagnose-груп. Некоректні необов’язкові options повертаються до дефолтів; якщо всі критерії вимкнені, порожній результат є коректним.

Без повторів типово 7 викликів на аналіз (1 + 5 + 1), або 6 без кандидатів для verifier; із повторами максимум 28 для п’яти груп. Rewrite/Refine має 1–3 спроби виправлення ops, кожна окремо використовує транспортні/форматні повтори `requestJSON` (до 9 викликів загалом). За вимкнення цілої групи викликів менше.

Eval описано у `backend/eval/README.md`. На реальному golden set якість ще не виміряна; checks є консервативними евристиками, а семантичний зв’язок доказу з твердженням оцінює LLM. Модуль не обчислює diff і не застосовує ops. Інтеграція з документами, БД і чатом — `services/ai/orchestrator.js` і `suggestionBuilder.js`.

## Кейси з перевіреними джерелами (`caseSources.js`, хвиля 5)

Опційно: `CASE_WEB_SEARCH=1` (за замовчуванням вимкнено). Для знахідок `PR-1`–`PR-3` групи practice (`PR-1` з `fixType: question` — лише коли є відповідь викладача) `generateSuggestion` перед rewrite:

1. робить виклик `createResponse` з `tools: [{ type: 'web_search_preview' }]` (вільний текст + `url_citation`);
2. окремим викликом `requestJSON('case_sources', …)` (strict `json_schema`) зводить знайдене до ≤ 3 кейсів `{ title, publisher, year, url, relevance }`;
3. перевіряє кожен URL на сервері (`verifyUrl`): http(s) без облікових даних, доменне ім'я з літерним TLD, порт 80/443, DNS лише в публічні адреси; `HEAD`, при відмові/обриві — `GET`, `redirect: 'manual'`, таймаут 5 с; підтверджено = 2xx/3xx;
4. передає моделі список з `verified` (URL лише в підтверджених) і після валідації `applyVerifiedSources` вирізає всі URL, яких немає серед підтверджених (з ops, опису, rationale, варіантів), додаючи до `description` «Джерело не підтверджено: …». Результат має `sources: [{ title, publisher, year, url, verified }]`.

Параметр `caseSources` (збережені джерела) пропускає пошук — так робить Refine. Збій пошуку не зриває генерацію: джерел немає, і будь-який URL у відповіді вирізається. У тестах `fetch` і `dns.promises.lookup` замінені mock-ами (`test/review/caseSources.test.js`).
